# Вход в Colors VPN через Telegram

Актуальное состояние передачи: 27 октября 2026. Создавать второй бот не требуется — настраивается существующий бот проекта.

## Что реализовано

`src/telegram-login.js`: Authorization Code Flow с PKCE S256, одноразовым state, browser binding, nonce, RS256/JWKS и проверкой issuer, audience, времени/срока токена. Подтверждённый числовой Telegram ID берётся из `id`, а не из username или OIDC `sub`.

Scope — `openid profile`. Код не запрашивает телефон/переписки и не даёт автоматически права на сообщения бота. Вход также не предоставляет роль администратора.

После callback создаётся серверная сессия на 7 дней: HttpOnly, Secure, SameSite=Lax, в SQLite хранится hash session token. OAuth access/ID tokens не сохраняются в пользовательской сессии и не отдаются браузеру. Внешний Telegram round-trip не проверялся: действующих настроек и HTTPS-домена в передаче нет.

Демо-сессии изолированы от настоящих; в текущем запуске `main.js` они тоже сохраняются в SQLite. Если OIDC включён даже в demo-процессе, настоящий вошедший аккаунт получает production-заглушку, а не демо-подписку.

## Текущее оформление

Вход открывается небольшим окном из общего интерфейса. `/account` использует тот же flow; отдельный кабинет без первых шагов покупки ещё не завершён после отката дизайна. Полноэкранный вариант сохранён в `design-versions/2026-10-24-telegram-login/` и не должен автоматически заменять `public/`.

## Настройка существующего бота

Владелец бота открывает BotFather → существующий бот → Login Widget:

1. Добавляет origin сайта, например `https://colors.example`.
2. Добавляет точный redirect URI `https://colors.example/auth/telegram/callback`.
3. Получает Client ID и Client Secret и задаёт их в защищённом окружении сервера.

```dotenv
PUBLIC_ORIGIN=https://colors.example
TELEGRAM_CLIENT_ID=
TELEGRAM_CLIENT_SECRET=
```

В текущем коде поддержан RS256. `.env` не включать в Git. `BOT_TOKEN` для site-OIDC не требуется; не задавать его в этом прототипе для уже работающего бота Вани, чтобы не запустить второй polling.

После заполнения `.env`, `ADMIN_IDS` и `ADMIN_TOKEN` (от 32 символов), при пустом `BOT_TOKEN`, non-demo запуск:

```sh
npm start
```

`npm run demo` и `start-demo.cmd` сами **не загружают `.env`**. Если нужно намеренно проверить OIDC в локальном demo-процессе, используйте явный запуск:

```sh
node --no-warnings --env-file=.env src/main.js --demo
```

Вошедший настоящий аккаунт при таком запуске всё равно получает production-заглушку; приём demo-чеков для него запрещён. Никакой из этих запусков не подключает автоматически backend Вани или панель.

Нужен HTTPS reverse proxy к loopback-серверу. Текущая проверка публичного Host включается только при наличии всего OIDC-конфига; перед production-интеграцией выделить её в независимую настройку, как описано в [запуске](docs/RUN_AND_DEPLOY.md).

## Что возвращается после входа

`/api/portal/session`: подтверждённый `account`, но `subscription:null`, `payment:null`, `subscriptionReady:false`, `paymentReady:false`. Реальный клиент/Remnawave ещё не привязаны.

Следующий шаг — найти в backend Вани существующего клиента по проверенному Telegram ID, получить его сохранённый panel user ID и вернуть реальные данные кабинета. Контракт: [docs/INTEGRATION.md](docs/INTEGRATION.md).

## Проверка

Серверная проверка OIDC входит в `npm test` — в полном наборе 35 тестов. Провайдер заменён контролируемыми ответами. Это подтверждает локальную проверку подписи, claims, state, PKCE, nonce, сессии и запрета повторного callback, но не доказывает работоспособность на конкретных настройках бота/домене.

Перед запуском пройти настоящий вход/выход/повторный вход, возврат после отказа Telegram, восстановление сессии после перезапуска, доступ к существующей подписке и отсутствие роли администратора у обычного пользователя.

Документация провайдера: https://core.telegram.org/bots/telegram-login
