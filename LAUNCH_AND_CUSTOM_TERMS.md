# Colors VPN: индивидуальные условия и запуск

Актуальное предложение от 24 октября 2026. Сценарий ниже — проект следующего этапа, а не описание уже работающей интеграции. Бот Вани остаётся действующим ботом. Второго production-бота и отдельной конкурирующей очереди не создаём.

## Что уже есть локально

- Сайт с тарифами, инструкцией, демонстрацией кабинета и отдельной страницей оферты.
- `/admin` — прототип ручной проверки, одобрения, выдачи и журнала. Открывается сразу раздел администратора. Его тестовая очередь пока не связана с новым порталом и backend Вани.
- Подготовлен серверный Telegram OIDC login; нужны настройки действующего бота, HTTPS-домен и проверка настоящего входа.
- Есть отдельный серверный RemnawaveReader с ограниченным набором возвращаемых полей. Он пока не включён в пользовательский API; версия и формат ответов панели требуют сверки.
- Вход Mini App, общие заявки сайта и бота, платежи, изменение лимита через панель и production-публикация ещё не подключены.

Старые упоминания обязательного email OTP в PORTAL_INTEGRATION.md не являются утверждённым требованием. Основной вход — Telegram. Независимый резервный способ входа понадобится только при отдельном решении о работе кабинета при недоступности Telegram.

## Условия на 4, 6, 8 и более устройств

1. Основные тарифы сохраняют 2 устройства. Под ними ссылка «Нужно больше устройств?»; такая же ссылка в кабинете.
2. Клиент выбирает 4, 6, 8… устройств, желаемый срок и при необходимости оставляет комментарий. Вход через Telegram до отправки сохраняемой заявки. В Mini App — подтверждённая сервером Telegram-сессия.
3. Сервер проверяет целое чётное число больше 2. Максимум — настраиваемый параметр сервиса, определяется возможностями инфраструктуры. Дополнительные цены не вычисляем по базовому тарифу без утверждённой формулы.
4. Администратор назначает цену за весь период, валюту/способ оплаты, срок и срок действия предложения. Поля цены изначально пустые. Клиент получает точные условия до оплаты.
5. Клиент принимает предложение; сервер сохраняет его неизменяемый снимок. Изменения до принятия создают новую версию предложения, после принятия — новое согласование.
6. После фактической проверки оплаты администратор отдельно одобряет выдачу. Нажатие клиентом «Я оплатил» только отправляет заказ на проверку и не устанавливает признак подтверждённой оплаты.
7. На первом этапе администратор выставляет срок и лимит в Remnawave вручную, затем backend читает фактические данные панели и подтверждает выдачу. Позже то же действие выполняет адаптер API после ручного одобрения.
8. Кабинет отображает новый лимит только после подтверждения панелью. При ошибке показываем «Доступ готовится», сохраняем задачу для повтора; не требуем повторной оплаты.

Для MVP индивидуальные условия меняют одну подписку и её лимит. Отдельные подписки для каждого члена семьи — иной продукт и не включены автоматически.

### Действующая подписка

Не пересчитываем доплату автоматически. Администратор явно задаёт новый лимит, дату окончания и сумму доплаты; клиент видит, продлевается ли срок. Отказ/неоплата заявки не изменяет действующий доступ. Продление считаем от более поздней даты: сейчас или действующий срок окончания. Календарные месяцы сохраняем календарными месяцами.

При уменьшении лимита ниже числа зарегистрированных устройств сначала согласовываем удаление конкретных устройств. Нельзя молча отключать случайные устройства. Совместимость Incy с HWID и поведение при достижении лимита проверяем на реальной панели отдельно для iOS/Android и остальных поддерживаемых платформ.

## Общая очередь и админка

Сайт и бот вызывают один сервис заявок backend Вани. UI `/admin` подключается к этому сервису вместо текущих демонстрационных заказов. Лимит, срок и цена проверяются сервером; стоимость не принимается из браузера как достоверная.

| Этап | Что видит клиент | Что делает администратор |
| --- | --- | --- |
| Запрошены условия | Заявка получена | Назначает цену, срок, лимит |
| Предложение готово | Условия и срок их действия | При необходимости выпускает новую версию |
| Ожидается оплата | Принятые условия и способ оплаты | Проверяет поступление |
| На проверке | Оплата проверяется | Подтверждает фактическую оплату либо отклоняет сообщение об оплате |
| К выдаче | Готовим доступ | Одобряет выдачу и применяет условия в панели |
| Активна | Ссылка, срок, устройства | Видит подтверждение синхронизации |
| Ошибка выдачи | Доступ готовится | Повторяет применение без повторного платежа |
| Отказ/истечение предложения | Причина и следующий шаг | Фиксирует причину; при полученной оплате ведёт отдельный возврат |

Карточка заявки: ID, Telegram ID и имя, источник (сайт/бот), существующая подписка, запрошенные/согласованные устройства, период, точная дата окончания, сумма и валюта, подтверждение платежа, история решений, ответственный администратор и состояние синхронизации.

Production-доступ: собственные администраторские сессии, список разрешённых Telegram ID, проверка полномочий на каждом серверном действии, дополнительная защита входа. Скрытая ссылка не даёт защиту. Текущий общий ADMIN_TOKEN — механизм прототипа, не окончательная модель командного доступа.

Заявки и события хранятся в общей БД backend, не в памяти браузера. Для параллельной работы — транзакции, проверка версии заявки и уникальная задача применения на заказ. Двойное нажатие «Одобрить» не должно повторно продлевать подписку. Запись решения предшествует обращению к панели; сбои доставляются в очередь повторов и журнал. Ручные изменения панели попадают обратно в кабинет через синхронизацию.

## Аккаунт сайта, Telegram и Remnawave

Общая запись: внутренний customer ID ↔ проверенный Telegram user ID ↔ сохранённый Remnawave user ID. Username служит только отображением и не используется как ключ. Тип panel user ID сверяется с установленной версией Remnawave.

- Первый вход с сайта: официальный Telegram OIDC, сервер проверяет подпись и claims токена, затем находит/создаёт внутреннего клиента. Отдельная регистрация не нужна. Код и пароль вводятся на стороне Telegram.
- Mini App: сервер проверяет подпись сырого initData и свежесть auth_date; доверять initDataUnsafe или user ID из запроса нельзя. Проверенный Telegram ID приводит к тому же customer ID.
- Существующие клиенты: переносим уже имеющуюся связь из backend Вани. Если связи нет, администратор сопоставляет существующую подписку до создания новой; не объединяем аккаунты по похожему имени.
- Разрешение на уведомления/доступный чат бота учитываем отдельно от самого факта входа на сайт.
- Браузер обращается к `/api/me` нашего backend. Backend по сохранённой связи читает панель и возвращает статус, expireAt, фактический deviceLimit, количество зарегистрированных HWID, безопасные названия устройств, subscriptionUrl и время обновления. Секрет панели остаётся на сервере.
- Обновление: чтение при открытии кабинета с небольшим кешем; подписанные webhooks для сброса кеша/изменений, периодическая сверка на случай пропуска события. Проверка подписи и повтора webhook обязательна.
- При недоступной панели сохраняем последнее подтверждённое состояние с временем обновления. Не показываем неизвестное число устройств как 0 и не восстанавливаем активность просроченной подписки из старого кеша.

HWID показывает зарегистрированные устройства, не активные соединения. Доступность точного ограничения зависит от клиента. В официальном списке совместимых приложений Remnawave Incy на дату проверки не указан; это не доказывает несовместимость, но требует реального теста до запуска лимитов.

## Публикация и доступ без VPN

Рекомендуемая схема: публичный HTTPS-сайт и его API на проверенном для нужных сетей хостинге; API по серверному соединению обращается к backend Вани/Remnawave. Панель может находиться в другом дата-центре. Доступность панели с телефона клиента для отображения кабинета не требуется.

Однако первое получение подписки приложением обычно обращается к домену subscription URL. Поэтому отдельно проверяем без VPN: лендинг, вход Telegram, API кабинета, загрузку Incy и домен выдачи подписки. Если домен подписок недоступен, нужен поддерживаемый публичный subscription endpoint на доступном хосте; административный API панели не открываем браузеру или приложению.

Требуется:

1. Домен под управлением проекта, DNS и HTTPS; сервер/контейнерный хостинг с постоянной БД и резервными копиями, reverse proxy, перезапуском процесса и мониторингом.
2. Статика, шрифты и API с собственного домена, без обязательных внешних CDN для отображения страницы. Это уже соблюдено в локальном интерфейсе.
3. Серверный сетевой доступ к панели или общему backend по защищённому каналу. Секреты в окружении/secret store; отдельный токен для интеграции, минимальные доступные права, ограничение сетевого доступа.
4. Действующий бот: настройки домена/redirect URI OIDC и кнопки Mini App, параметры проверки initData на backend, список администраторов.
5. Подключённая общая БД клиентов и заказов; согласованные API чтения кабинета и ручной обработки заявок. Платёжный сценарий проверяется отдельно для обычного сайта и Telegram Mini App.
6. Приёмочные проверки без VPN из нескольких домашних и мобильных сетей РФ: DNS/TLS, главная, вход, заявка, кабинет, установка, первое получение/обновление подписки. Одной проверки из сервера или одной сети недостаточно.

Нельзя гарантировать доступность во всех сетях РФ выбором страны хостинга или CDN. При региональных ограничениях и изменениях блокировок нужен мониторинг и повторные проверки. Если Telegram недоступен в сети пользователя, сайт и инструкции могут открываться, но новый вход только через Telegram тоже будет недоступен. Для автономного от Telegram кабинета необходимо отдельно добавить резервный подтверждённый вход, например email-код, с безопасной привязкой к существующему customer ID.

## Какие сведения нужны для подключения

- Версия и base URL установленной панели; включён ли HWID, как сформирована subscription URL.
- Username действующего бота и кто управляет его BotFather; текущие способы входа и хранения клиентов у Вани.
- Схема связи Telegram ID → Remnawave user ID и доступные backend endpoints. Для согласования достаточно схемы/обезличенного примера, не выгрузки персональных данных.
- Кто будет администраторами, какие действия разрешены, как сейчас подтверждают оплату.
- Домен, доступ к DNS, выбранный хостинг и возможность сетевого доступа к backend/панели.
- Секреты и токены передаются при настройке через защищённое окружение; в переписке они не нужны.

Порядок запуска: общая идентичность и read-only кабинет → общая очередь и ручная выдача → проверка лимитов → production-хостинг и тестирование из РФ → реальный платёжный сценарий. Платежи не открываем раньше проверенного пути выдачи.
